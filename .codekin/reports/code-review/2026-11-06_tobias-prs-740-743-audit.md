## #740 — Native macOS folder dialog

**Scope:** `server/native-folder-picker.ts` (new), two routes in `server/session-routes.ts`, `FolderPicker` UI, plus an unrelated OpenCode ENOENT fix and a `.conductor/` gitignore entry.

**Verification:** 5 test files / 233 tests pass; frontend `tsc` clean; eslint 0 errors.

### Security review

- Both routes require the auth token.
- The gate in `isNativeFolderPickerAvailable` (`server/native-folder-picker.ts:30`) allows the dialog only when:
  - the server runs on `darwin`
  - `req.socket.remoteAddress` is loopback (not `req.ip`, so `trust proxy` can't spoof it)
  - there is no `X-Forwarded-For` header
- `/api/native/*` is not on the relay connector allowlist, and a test pins that. The hosted app cannot reach the routes.
- The starting folder goes to `osascript` as argv, never into the script text. It must be an absolute existing directory, so it can't start with `-`.
- The picked path is still canonicalized by the existing save path (`canonicalizeReposPath`).

### Findings

1. **Low — locality heuristic can be fooled by forwarders that add no `X-Forwarded-For`.**
   - Affected: an SSH `-L` tunnel, or `vite --host`, whose proxy has `xfwd` off.
   - Effect: a remote client looks local, and the dialog opens unseen on the Mac. The request then holds the single-dialog lock for up to 10 minutes.
   - Impact: limited to the token holder; nuisance only. Acceptable.
2. **Low — `inFlight` stays `true` forever if `execFile` throws synchronously** (`native-folder-picker.ts:100`). That makes the route 409 until restart. Very unlikely; a `try` around the call would close it.
3. **Note — behaviour change:** a native pick saves immediately, without the explicit Save step the text input needs. This is intentional per the PR description.
4. **Note — the OpenCode fix is correct and worth having:**
   - it adds an `'error'` listener on the spawned process, so ENOENT no longer becomes an uncaught exception
   - it fails fast instead of polling for 30 s
   - it's bundled into a feature PR, but small.

## #741 — Composer permission modes, Shift+Tab, tint

**Scope:** `src/lib/permissionModes.ts` (new), `InputBar.tsx`, `PermissionsSection.tsx`, `index.css`, two new prefs.

**Verification:** 38 tests pass; frontend `tsc` clean; eslint 0 errors. The author notes it was **not checked visually across the nine themes**.

### Findings

1. **High (policy) — dangerous-mode confirmation weakened from every time to once ever.**
   - `confirmDangerousMode` (`InputBar.tsx:138`) records the confirmation in the server-side `confirmedDangerousModes` pref.
   - That pref is shared by every device and browser of the install.
   - After one "yes", switching to Bypass / Skip permissions never asks again, from the menu or from Shift+Tab.
   - This reverses a deliberate safety prompt. It needs an explicit product decision, not a side effect of a cycling feature.
2. **High (UX / safety) — Shift+Tab cycles into dangerous modes by default.**
   - `enabledPermissionModes` unset means *all* modes (`permissionModes.ts:17`).
   - So by default the ring includes Bypass and Skip permissions.
   - Combined with #1, a user who once confirmed Bypass can land in it by overshooting Shift+Tab while typing, with no prompt.
   - Recommendation:
     - leave dangerous modes out of the Shift+Tab ring unless explicitly enabled (Claude Code's own cycle excludes bypass by default)
     - and/or always confirm when *cycling* into one.
3. **Medium (visual) — the danger tint re-points ink tokens but not surface tokens, so hover states break in dark themes.**
   - `.composer-card[data-mode-tone="danger"]` (`index.css:752`) sets `--color-ink*` to near-black.
   - Children still use `hover:bg-surface-raised` / `hover:bg-edge`. Examples:
     - `ToolbarAction` (`InputBar.tsx:50`)
     - the state chips
   - In dark themes those hover backgrounds stay dark, so icons and labels turn dark-on-dark on hover.
   - Popover children are restored only if they carry `.rounded-floating`, which is fragile.
4. **Medium (styling rules) — raw colour literals in `index.css`.**
   - The danger block hard-codes `white`, `#1c1a18`, `#57524c`, `#8a847c`, `#a12c2c` and `black` mixes.
   - It also forces a near-white card in every theme.
   - CLAUDE.md asks for polarity tweaks on `[data-scheme=…]` and theme-driven colour. These should be tokens, or at least scheme-scoped, and checked against all nine palettes.
5. **Low (a11y) — Shift+Tab in the textarea no longer moves focus backwards.** Keyboard users can't tab out of the composer in reverse. This copies a CLI convention, but should be called out (or use a different chord).

## #742 — Tauri desktop app plan (docs only)

**Scope:** `docs/DESKTOP-APP-TAURI-PLAN.md`, a draft proposal. The referenced code facts check out on `main`:
- `FRONTEND_DIST`, `AUTH_TOKEN_FILE`, `DATA_DIR`, `BIND_HOST`
- `/api/health` with `claudeAvailable`
- the npm `files` set

### Findings

1. **Low (formatting) — stray Non-goals bullet.** Line 34 ("Intel Macs, Windows and Linux builds…") sits after the coexistence table instead of under *Non-goals*.
2. **Medium (design gap) — version skew on a shared `DATA_DIR`.**
   - The app is versioned independently but shares `~/.codekin` with an npm-installed service.
   - An older bundled server can run against a database already migrated by a newer service, or the other way round.
   - The plan should define a schema/version check, and refuse or warn on mismatch.
3. **Medium (design gap) — service restarts.**
   - "Attached service stops → the app starts its bundled server" will grab the port during a normal `codekin service` restart or upgrade.
   - The launchd service then fails to bind and, with KeepAlive, restart-loops.
   - The plan needs a grace period, or should defer to an installed service.
4. **Low — health-probe identification.** "Any HTTP response means the server is up" can't tell Codekin from another app on the port. Yet the plan also promises a "port taken by something that isn't Codekin" view. The probe should check the response shape.

## #743 — Per-session reasoning effort

**Scope:**
- Server: `--effort` for Claude; `turn/start.effort` plus `config.model_reasoning_effort` for Codex.
- Protocol: new `set_effort` WS message, and an optional `effort` on `set_model`.
- Client: persisted session field, picker UI, ⌘⇧E / Ctrl+Shift+E shortcut.

**Verification:**
- 7 test files / 496 tests pass; frontend `tsc` clean; eslint (`--quiet`) clean.
- Checked against the installed CLIs:
  - `claude --effort <low|medium|high|xhigh|max>` exists in Claude Code 2.1.316; Haiku accepts `--effort max`.
  - Codex app-server 0.157.1 (generated schema):
    - `TurnStartParams.effort` exists ("Override the reasoning effort for this turn and subsequent turns")
    - `ThreadStartParams.config` and `ThreadResumeParams.config` exist
    - `Model` carries `supportedReasoningEfforts` / `defaultReasoningEffort`
- The PR's mechanism matches the protocol.

### Findings

1. **Medium (UX) — every Claude effort change is a full stop/restart, now one keystroke away.**
   - `setEffort` (`session-manager.ts:1607`) goes through `coordinator.requestReconfigure`, which calls `doStop()` immediately and interrupts an in-flight turn.
   - Model changes already behave this way, but a repeatable global shortcut makes it easy to fire several restarts in a row (one per press).
   - Suggest one of:
     - debounce the shortcut
     - for Claude, defer the restart until the session is idle.
2. **Low — effort is validated by shape only.**
   - `validEffort` accepts any `^[a-z][a-z0-9_-]{0,23}$`.
   - A shape-valid but unsupported level (e.g. `minimal` on a Claude session from a stale client) is persisted, and the CLI fails on every restart until the effort is cleared.
   - Validating against `CLAUDE_EFFORTS` for Claude sessions would prevent that.
3. **Low — the shortcut is a global `window` keydown listener** (`InputBar.tsx:868`). It fires even while focus is in other inputs (settings fields, dialogs). Only one composer is mounted at a time, so it doesn't double-fire.
4. **Low — the effort change isn't broadcast.** Other clients viewing the same session show stale effort until they rejoin, the same as the existing `set_model` behaviour.
5. **Nit — orphaned doc comments.**
   - `validEffort` was inserted between `modelFitsProvider`'s JSDoc and the function, so `modelFitsProvider` lost its doc.
   - The same thing happened with `ModelOption` in `src/types.ts`.

### #741 rework

- The card's background and border now come from the theme: its own surface tinted toward its error hue, scheme-scoped.
- The ink and edge tokens are no longer re-pointed, so there are no hex literals and no `.rounded-floating` restore.
- The mode chip uses `error-4` instead of `warning-4`.
- Measured in Chromium:
  - before: hovers in the six dark themes were 1.02–1.31:1
  - after: every text pair on the card, its hovers and its popovers is ≥ 4.5:1 in all nine themes.

### #743 fixes

- **Debounce:** `set_effort` is sent after a 400 ms pause, so stepping through levels costs one restart. A pending level is sent before a session switch, and dropped when `set_model` carries its own effort.
- **No mid-turn restart:** while a Claude turn is running, the new level is recorded and the restart waits for the turn's result.
- **Validation:** Claude sessions accept only `low`/`medium`/`high`/`xhigh`/`max`.
- **Doc comments:** the orphaned comments are restored.

### #741 policy decisions (resolved, commit `4c6b6fb`)

- **Ask every time:**
  - Bypass and Skip permissions confirm on every switch again, as on `main`.
  - The `confirmedDangerousModes` pref, its Settings list and the "Ask again" button are removed.
- **Never in the Shift+Tab cycle:**
  - The two dangerous modes are never in the Shift+Tab ring, even when enabled. They are reachable only from the mode menu.
  - From a dangerous mode, Shift+Tab steps to the first enabled safe mode without a prompt.
  - Reason: a keystroke made while typing must not switch approvals off, and a confirm on every lap would train people to click through it.
